# Audit Export Workflow

The goal, stated plainly: **produce everything a six-month insurance audit asks
for, as one organized ZIP, without searching email or folders.**

---

## 1. Create the audit cycle

`/ops/audits` → the form pre-fills a trailing six-month window ending today and
a name like `2026 H2 Insurance Audit`.

| Field | Note |
|---|---|
| Name | Free text, e.g. `2026 H1 Insurance Audit` |
| Period start / end | The window the auditor asked about |
| Due date | Optional, for your own tracking |
| Status | draft → preparing → ready → submitted → closed |
| Notes | Who is auditing, what they asked for |

---

## 2. Review who is in scope

Open the cycle. Vertical Ops works out the vendor list itself — a subcontractor
is included if **either**:

- **they were assigned to a project overlapping the window**, or
- **they held coverage overlapping the window**

Both, because an auditor cares about who worked *and* what was on file.

The table shows, per vendor: trade, projects in the period, a Covered/Gap chip
per coverage type, status **at period end**, status **today**, and document
count. Narrow with project, trade, compliance-status and coverage-type filters
if the auditor scoped their request.

### The overlap rule

```
policy.effective_date <= period_end   AND   policy.expiration_date >= period_start
```

Inclusive at both ends. A policy that expired on the first day of the window
counts; one that started the day after it closed does not. Unrecorded dates are
treated as overlapping, so nobody is dropped from an audit because a field was
left blank.

Compliance is evaluated **as of the end of the audit period**, not today. Both
are shown, and they are often different — that is correct.

---

## 3. Generate the package

**Generate audit package** → optionally narrow the filters → the ZIP is built
server-side, written to private storage, and recorded in `audit_exports`.

```
Vertical_Builders_2026_H1_Insurance_Audit/
│
├── README.txt                          How coverage was determined + counts
├── 00_Audit_Summary.pdf                One-page overview and per-vendor findings
├── 01_Compliance_Register.xlsx         4 sheets (below)
├── 02_Compliance_Register.csv          Same register, plain CSV
├── 03_Missing_Expired_Exceptions.csv   Gaps and documented exceptions only
├── 04_Activity_Log.csv                 Who touched compliance records, in-period
│
└── 05_Subcontractors/
    ├── ABC_Roofing_Systems_LLC/
    │   ├── Vendor_Summary.txt
    │   ├── Certificate_of_Insurance_2026-01-01_COI.pdf
    │   ├── Insurance_Endorsement_GL_Endorsement.pdf
    │   ├── W-9_W9_2026.pdf
    │   └── Contractor_License_License.pdf
    └── XYZ_Drywall_Finish_Inc/
        └── …
```

### Workbook sheets

| Sheet | Contents |
|---|---|
| **Summary** | Period, generation timestamp, all counts, the disclaimer |
| **Compliance Register** | 44 columns — vendor, trade, projects, both statuses, GL/WC/Auto/Umbrella blocks (carrier, policy #, dates, limits, covered-in-period), AI/WOS/P-NC flags, license, W-9, counts, reviewer, exceptions, gaps. Frozen header + autofilter. |
| **Missing & Expired** | One row per gap or exception |
| **Policy Lines** | Every in-period policy line with full limits and an explicit "overlapped audit period" column |

### Graceful degradation

CSV is generated by a dependency-free writer in `lib/ops/utils/csv.ts` and is
**always** produced. If the XLSX or PDF step throws, the package still builds and
a note is added to `README.txt` and returned to the UI. The audit is never
blocked by a formatting library.

---

## 4. Reproducibility

Every generation writes a **new** object and a **new** `audit_exports` row:

```
audit-exports/{auditCycleId}/Vertical_Builders_{name}_{ISO-timestamp}.zip
```

Nothing is ever overwritten. The row stores `filters_json` (exactly how it was
built) and `snapshot_json` (summary counts plus a per-vendor record of status,
projects and policy-line count at generation time).

There is **no DELETE policy** on `audit_exports`, `insurance_certificates`,
`insurance_policies` or `compliance_reviews` — not even for admins. A package
handed to an auditor in March still downloads, byte for byte, in September.

Downloads go through `/api/audits/{exportId}/export`, which authenticates,
checks the role, mints a 10-minute signed URL, logs the download, and redirects.

---

## 5. Safety limits

| Guard | Value | Behaviour at the limit |
|---|---|---|
| Documents per package | 400 | Stops adding, adds a warning to `README.txt` and the UI |
| Package size | 180 MB | Same |
| Activity log rows | 5,000 | Most recent in-period entries |
| Function timeout | 60 s | Set in `vercel.json` |

If you hit a limit, narrow by project or trade and generate a second package.
Both remain downloadable.

## 6. Questions this answers in seconds

| Question | Where |
|---|---|
| Which subcontractors are compliant right now? | `/ops/compliance`, filter Compliant |
| Which are missing insurance? | Same, filter Missing |
| What expires in 7 / 30 / 60 days? | Dashboard KPI → filtered register |
| Who worked on Project X? | Project → Subcontractors tab |
| Which certificates were active during the audit period? | Audit cycle table |
| Who was active during that period? | Same — assignment dates drive it |
| What was on file at the time? | `05_Subcontractors/{vendor}/` |
| Can I download everything for an auditor? | Generate audit package |
| Can I export a spreadsheet of the register? | `01_…xlsx` / `02_…csv` |
| Who uploaded, reviewed or changed a record? | `/ops/activity` and `04_Activity_Log.csv` |
| Who should not be scheduled? | Compliance register — red rows; project pages banner it |
